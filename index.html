RAG Architecture (How It Works)

  • Upload — Document split into chunks using the selected strategy.
  • Embed — Each chunk converted to a 1024-dim vector via mxbai-embed-large.
  • Store — Vectors saved in Qdrant; chunk text, chats, and metadata saved in SQL Server.
  • Query — User question embedded and hybrid search runs:
    • Vector search — cosine similarity in Qdrant (70% weight)
    • BM25 search — keyword matching against cached chunk text (30% weight)
    • Fusion — scores combined: final = 0.7 × vector + 0.3 × bm25
  • Retrieve — Top-K chunks above the minimum score returned (TopK, weights, and thresholds are configurable).
  • Generate — Retrieved chunks sent to llama3.2:3b as context.
  • Stream — LLM response sent token-by-token to the client via SignalR.

Vector Store (Qdrant)

  • All dense vectors live in Qdrant behind an IVectorStore interface, run with Docker Compose.
  • Deleting a document removes its points from Qdrant, and the server refuses to start with a clear message if Qdrant is not running.
  • Changing the embedding model needs a new collection name (vector size is fixed per collection), then a re-upload.
  • A stats endpoint reports provider, total chunks, and total documents.

Chunking Strategies

  • FixedSize — Splits text into fixed 500-char chunks with 100-char overlap. Fast, works for most documents.
  • ContentAware — Respects sentence boundaries, markdown structure, and paragraphs (100–1000 chars). Best for structured documents.
  • Semantic — Groups sentences by topic coherence using word-overlap similarity (150–1200 chars). Best for dense research papers.

Multilingual Support (English, Thai, Khmer)

  • English — word tokenization with stop word removal for BM25.
  • Thai & Khmer — character trigram (n-gram) tokenization since these languages have no spaces between words.
  • Auto-detects script per text segment, handling mixed-language documents correctly.
  • All 3 chunking strategies support language-specific sentence boundaries (Thai ๆ/ฯ markers, Khmer ។ terminator).

RAG Evaluation

  • No reference answer needed — the system auto-generates one from retrieved chunks via LLM, using the RAG's own settings (passages, relevance, instructions, model).
  • Pipeline: Hybrid search → LLM generates reference answer → LLM generates RAG answer → BLEU/GLEU/F1 compare both → LLM Judge scores semantic quality.
  • BLEU — n-gram precision. GLEU — balanced precision and recall. F1 — token overlap (SQuAD-style). LLM Judge — semantic score (0–10 normalized to 0–1), most reliable for Thai and Khmer.
  • Every run is saved to a history (newest 50 kept) with both answers and all settings used, so runs can be compared side by side and exported to CSV. An optional stronger judge model can be configured.
  • Pure NLP evaluators (BLEU, GLEU, F1) kept separate from DI services; exposed through a REST API (run, list, read, delete).

Accounts and Chat Experience

  • ASP.NET Core Identity with JWT login; the login key and first admin are stored as user secrets, not in git.
  • Each person has their own chats and RAGs (Settings > My RAGs: Knowledge, Settings, and Evaluation tabs).
  • Chat sidebar with pin, rename, and delete; theme button cycles System, Light, and Dark and remembers the choice.

Intelligent RAG Routing

  • System automatically decides whether to answer with document context or LLM-only — no manual switching needed.
  • Question embedded → hybrid search runs across all cached chunks → scores calculated.
  • If best chunk score ≥ 0.65: answer uses LLM + RAG context, sources shown in chat.
  • If no chunks pass threshold: LLM answers from its own knowledge only, no sources shown.
  • Prevents irrelevant document context from being forced into unrelated answers.
  • Threshold configurable in rag_service.py — lower for more RAG, higher for stricter matching.

Hybrid Search (Vector + BM25)

  • Combines two complementary retrieval methods: Vector Search (cosine similarity, 70%) and BM25 keyword search (30%).
  • Formula: final = 0.7 × vector_score + 0.3 × bm25_score
  • Vector search handles semantic meaning and paraphrasing; BM25 handles exact terms, technical names, and IDs.
  • Weights configurable via .env — VECTOR_WEIGHT and MIN_SIMILARITY_THRESHOLD.

Chunking Strategies

  • FixedSize — 500-char chunks with 100-char overlap. Fast, good for most documents.
  • ContentAware — Respects headings, paragraphs, and sentence terminators (100–1000 chars). Best for markdown and structured docs.
  • Semantic — Groups sentences by topic-overlap similarity (150–1200 chars). Best for research papers and dense content.

Multilingual Support (English, Thai, Khmer)

  • English — word tokenization with stop word removal for BM25; punctuation-based sentence splitting for chunking.
  • Thai — uses pythainlp word tokenizer (newmm engine) for BM25 and sentence tokenizer for chunking; trigram fallback if not installed.
  • Khmer — character trigram tokenization for BM25; splits on ។ ៕ ៖ sentence terminators for chunking.
  • Auto-detects language per text segment using Unicode range detection.

In-Memory Embedding Cache

  • Singleton service — holds all embeddings as numpy float32 arrays in a thread-safe ConcurrentDictionary.
  • Startup pre-warming: loads all Ready chunks from SQL Server before first request.
  • Partial updates: uploading a new document adds only its chunks; deleting removes only that document's chunks — no full reload needed.
  • Cache stats endpoint: GET /api/documents/cache-stats — total chunks, documents, and estimated RAM.
  • Memory estimate: ~4MB per 1,000 chunks, ~40MB per 10,000 chunks.

RAG Evaluation Pipeline

  • No reference answer needed — LLM auto-generates an ideal reference from retrieved chunks.
  • Pipeline: Hybrid search → LLM generates reference → LLM generates RAG answer → BLEU/GLEU/F1 score both → LLM Judge scores semantic quality.
  • BLEU — n-gram precision for factual phrase accuracy.
  • GLEU — balanced precision + recall, penalizes wrong additions and missing content.
  • F1 — token overlap, standard SQuAD benchmark metric.
  • LLM Judge — scores 0–10 normalized to 0–1, reliable for multilingual (Thai/Khmer) evaluation.
  • Overall score = average of all 4 metrics.

  • Model Training — Trains 3 models simultaneously on the full training set.
  • Model Evaluation — Runs k-fold cross-validation, evaluates on held-out test set, extracts feature importances, selects best model by highest CV mean score.

  • Feature importance extracted from feature_importances_ (tree models) or coef_ (linear models) — top 15 features returned.

Jamoon Skincare Store — Online Shop + POS with Automatic KHQR Payments

August 2025

A complete English and Khmer skincare shop in one small system: customer website, admin panel, counter POS, and automatic KHQR (Bakong) payments. The website and the staff POS share the same products, stock, orders, and reports. It runs as two processes and one SQLite file, so it fits on a laptop or a small VPS.

Key Features:

  • Built the storefront: catalogue with skin-type filter and search, reviews, wishlist, cart, coupons, guest checkout, order tracking, saved addresses, printable receipts, and an installable PWA.
  • Integrated automatic KHQR payments through Bakong. Each order gets its own QR with the exact amount and a 15-minute expiry, and the order confirms itself, checked by page polling and a server sweep every 20 seconds. A payment with the wrong amount is never confirmed and goes to an admin review list.
  • Built a counter POS with barcode scanner support, discounts (owner / manager), cash change calculator, mandatory payment photo for bank or QR sales, printable receipts, and sales history.
  • Added owner-only cost and profit tracking. Costs live in separate tables, with the cost frozen onto every order line, so no public route can leak them. A smoke test scans every public response to prove it.
  • Built the admin panel: dashboard comparing online and POS sales, fulfilment board (new, packing, packed), returns and refunds, inventory, coupons, reviews, an Excel / CSV Export Center (9 workbooks), and Excel product import.
  • Added 4 staff roles (owner, manager, packer, cashier) with permissions decided in one server file; Telegram alerts for new orders, payments, low stock, and orders stuck over 24 hours; and e-mailed password reset.
  • Fully bilingual (English and Khmer, 2,484 strings each), with a check that fails the build if the two languages differ.
  • Backed by 968 automated checks (684 API smoke, 254 frontend, 30 dashboard and Bakong tests), plus architecture and type checks.

Architecture

  • The website never touches the database; it only calls the REST API. Prices, stock, totals, coupons, and admin rights are all decided in the backend.
  • Every request passes helmet and CORS, a rate limit (login, register, reset), JWT auth, permission checks on admin routes, and zod validation before the business rules run.
  • Backend layers go one way: routes (HTTP) → lib (rules) → db. The frontend has its own enforced layer order, checked by an architecture script.
  • One status table governs every order change, whether from a click, a bulk action, or an automatic payment. Cancelling puts items back in stock and releases the coupon.

Payments

  • KHQR (Bakong), ABA / Wing with receipt upload and admin verification, and cash on delivery.
  • KHQR runs in Live, Test, or Off mode, decided by the server environment and never by the browser.
  • A customer who pays and closes the page is still confirmed by the server sweep.

Database (SQLite, 19 tables)

  • Created and upgraded automatically on start. Foreign keys cascade or null out on purpose, so deleting a product never destroys order history.
  • Order items copy the product name and price, and orders keep their own copy of the address, so past orders stay correct after edits.
  • Password reset tokens are stored only as hashes; coupons are referenced by code so deleting one never breaks old orders.

Security and Sessions

  • bcrypt password hashes; JWT lifetime 7 days for customers and 12 hours for admins.
  • Admin session ends when the browser closes unless "Remember me" is ticked, and signs out after 30 minutes idle.
  • JSON limited to 200 kb and uploads to 2 MB; the API refuses to start in production without a strong secret.
  • Admin changes and sign-ins are recorded in an Activity log with no secrets.
  • Unlisted admin routes are owner-only by default, so a new feature stays hidden from staff until access is granted.

Background Workers and Deployment

  • KHQR sweep every 20 seconds; a watchdog every 15 minutes checks for low stock and paid orders waiting over 24 hours, and reports each problem once.
  • Deployed with Caddy (automatic HTTPS) and Cloudflare in front; the frontend is hosted on Vercel.
  • Documented in a docs/ folder with architecture, recipes, per-feature guides, and a changelog.

  • Backend: Node.js, Express, zod, JWT, bcrypt, helmet
  • Database: SQLite (better-sqlite3)
